# 島流旅綠幣 IslandFlow — 概念驗證版 iOS App

台灣好行北投竹子湖線的「動態觀光任務與獎勵層」。旅客比較班次 → 加入任務 → 起點／終點掃站牌動態碼 →
旅綠幣入帳 → 在合作小農店家兌換；管理者即時看到獎勵成本、新增搭乘、地方消費、分流與估算減碳。

原生 SwiftUI + SwiftData，iOS 17+，**單機運作、不需要任何後端或帳號**，黑客松展示用。

**接手或回來繼續開發，先看 [docs/接手筆記.md](docs/接手筆記.md)**（目前狀態、下一步）；
來龍去脈與設計決策在 [docs/開發筆記.md](docs/開發筆記.md)。

> 規格書建議的是 Next.js + Supabase 網頁版；依團隊決定改做原生 iOS App 方便現場手機展示。
> 規格中的資料表、唯一限制、交易與冪等性都照做，只是資料庫從 Postgres 換成手機上的 SwiftData。

## 用到的真實開放資料

| 資料集 | 用途 | 檔案 |
|---|---|---|
| 交通部觀光署 台灣好行站點資料（93967） | 北投竹子湖線任務用 9 站（去程）與回程站序 | `IslandFlow/Resources/opendata_93967_beitou_zhuzihu_stops.csv` |
| 同上，全台原檔（2026-09-29 下載快照，未修改） | 唯讀路線目錄：北投竹子湖／獅山／南庄去回程站序 | `IslandFlow/Resources/opendata_93967_taiwantrip_all_20260929.csv` |
| 臺北市觀傳局 北投竹子湖線每月搭乘人次（172679） | 管理端「路線與班次」月搭乘率圖 | `IslandFlow/Resources/opendata_172679_*.csv` |

**簡報可以用的背景（注意說法）：** 115 年 1～8 月平日「月總搭乘人次 ÷ 月總座位供給」為 124%～160%（每班 19 座）。
途中有人上下車時同一座位會被算好幾次，所以這**不能說成某一班超載**，只能當月度運量偏高的背景；
哪些班次擁擠需要班次或區間資料。App 首頁的 09:10 尖峰班次與各班載客率都是示範值。

其餘（各班次預估載客率、三家商家、過去 14 天的參加與核銷）都是模擬資料。旅客首頁常駐「示範模式」提示，
班次標「示範班次」、舒適度標「示範預估」、虛構店家標「示範店家・尚未提供真實兌換」；管理端照舊掛「示範資料」。

## 裝到自己的 iPhone（免費 Apple ID）

1. 用 Xcode 打開 `IslandFlow.xcodeproj`
2. 左側點專案 → TARGETS `IslandFlow` → Signing & Capabilities → Team 選你的 Apple ID
   （預設是 `F3J4S8V4CB`，跟行旅手札同一個；Bundle ID 是 `com.thomaslin.islandflow2026`）
3. iPhone 接電腦、上方選你的手機 → ⌘R
4. 第一次要在 iPhone「設定 → 一般 → VPN 與裝置管理」信任開發者

注意：
- 免費簽章 **7 天到期**，比賽前一兩天重跑一次最保險（資料會保留）
- 免費帳號同時最多 **3 個自簽 App**；行旅手札已佔一個
- 要兩支手機展示時，另一支也照做一次（可以用同一個 Apple ID）

## 三分鐘展示腳本（對應規格書「展示腳本」）

一般使用者打開 App 直接是旅客模式，看不到任何展示工具。展示用的東西都收在**展示選單**：

- 旅客頁：**長按左上角「島流旅綠幣」字樣**（約 1 秒）
- 歡迎頁：長按中間的圖示
- 商家／管理者頁：右上角的面具按鈕

開始前：展示選單 →「重置示範資料」。

| 時間 | 身分 | 操作 | 要講的重點 |
|---|---|---|---|
| 0:00 | — | 開場 | 固定補助無法精準補離峰、也追蹤不到地方消費 |
| 0:20 | 旅客・小綠 | 探索首頁 | 推薦 10:40「較舒適・示範預估」100 枚；13:10「普通」80 枚；09:10「較擁擠」無旅綠幣。頂端常駐示範模式提示 |
| 0:30 | 旅客 | 展示選單 →「調整班次預估載客率」→ 13:10 拖到 25% → 完成 | **首頁 13:10 立刻變 100 枚**（評審記憶點） |
| 0:40 | 旅客 | 推薦卡「查看任務」→「加入任務」 | 底部按鈕自動變成下一步「掃描出發碼」 |
| 0:55 | 旅客 | 「掃描出發碼」→ 展開「防弊情境」→ 錯誤站點、過期的碼 | 系統拒絕並說明原因 |
| 1:05 | 旅客 | 「模擬掃描站牌」→「好，出發！」→「掃描到站碼」→「模擬掃描站牌」 | 「已獲得 100 枚」、竹子湖站附近 2 項兌換品；下方有交通排放明細（示範估算、不算減碳）與「查看回程」 |
| 1:20 | 旅客 | 點「海芋小花束」→「確認兌換」 | 完成任務後兩次點擊就拿到 QR；使用 60 枚、剩 40 枚 |
| 1:35 | 旅客→商家 | QR 下方「切換到「湖田小農市集」核銷」→ 待核銷兌換碼 → 確認兌換 → 展開「防重複展示」→ 重送 | 扣點扣庫存同一筆交易；重送不重複扣 |
| 2:00 | 管理者 | 展示選單 → 觀光主管機關 → 政策效益 | 「本次展示即時產生：完成 1、核銷 1」；政策槓桿、每新增搭乘成本、分流、減碳 |
| 2:30 | 管理者 | 班次 → 月搭乘率圖 | 真實開放資料：月度運量偏高（人次÷座位供給，不等於單班超載）；同頁可進「路線目錄匯入」看全台 CSV 檢查報告 |
| 2:40 | — | 收尾 | 不重做環保集點；正式版串既有點數，島流負責任務編排與政策成效 |

想展示旅客端的「兌換成功」畫面：QR 下方按「模擬店員掃描」（走的是和商家端相同的核銷流程）。

**兩支手機的玩法：** 手機 B 切到管理者 → 更多 → 站牌動態碼看板（每 30 秒換碼），手機 A 旅客用相機掃。
站牌碼是簽章碼，兩支手機不用連線也能驗。**但商家核銷必須在同一支手機切換身分**（見下方限制）。

展示選單裡可以關掉「掃碼頁顯示模擬掃描」，讓畫面跟一般使用者完全一樣。

## 功能對照（規格書編號）

- 旅客（三個分頁：探索／行程／綠幣）：T01 探索首頁（推薦卡＋比較列）、T02 詳情（地圖、算法收進展開區）、
  T03 加入（重複點擊只一筆）、T04/T05 兩階段驗證（過期、錯站、錯班次、偽造、重複掃描、未出發先到站都會拒絕並說明）、
  T06＋T07 綠幣中心（餘額、可選品項數、任務終點附近、沿線店家、使用紀錄；只列合作店家）、
  T08 兌換三步驟（確認 → QR＋短碼等待掃描 → 兌換成功）；行程頁未出發可取消、完成後可看回程；
  探索頁「查看其他台灣好行路線」唯讀目錄（北投竹子湖／獅山／南庄，去回程站序與地圖）
- 商家：M01 示範帳號、M02 掃碼／短碼預覽（確認前不扣點）、M03 單一交易確認＋冪等鍵、
  M04 核銷紀錄（含失敗原因，只看得到自己的店）
- 管理：A01 路線班次（開放資料＋載客率滑桿＋全台路線目錄匯入預覽）、A02 任務管理、A03 獎勵規則（級距表／加權分數兩種模式，
  即時預覽）、A04 商家與獎品（is_partner、庫存）、A05 政策儀表板（11 項指標＋定義）、
  資料來源與估算假設（可調）、站牌動態碼看板、稽核紀錄

## 測試

```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer xcodebuild -project IslandFlow.xcodeproj \
  -scheme IslandFlow -destination 'platform=iOS Simulator,name=iPhone 17 Pro' test
```

61 個單元＋整合測試：獎勵計算、權杖簽章／到期／竄改、碳排估算（含每人／每車公里、負差值、缺值）、
儀表板指標定義、開放資料解析、班次可參加性排序、取消任務（擁有者、出發後不可取消）、
CSV 引號／逗號／BOM／CRLF、全台原檔檢查報告（2,585 列、97 名稱、7 筆座標異常、1 組重複站序）、
三路線去回程、重匯冪等、寫入失敗保留上一版、壞檔不覆寫、目錄不動任務資料；
整合測試跑完整流程（重複加入、每日上限、名額、無庫存停發、錯誤驗證、只入帳一次、定位檢查、
核銷冪等、過期碼留紀錄、跨商家權限、非合作店家、儀表板即時更新）。

6 個 UI 測試（XCUITest，真的點畫面）：旅客完整任務到 QR 與兌換成功（含出發驗證完成標題）、商家掃碼到核銷成功、
綠幣中心只列合作店家與示範店家標示、行程頁取消任務、唯讀路線目錄、歡迎頁進探索。每個關鍵畫面都會存截圖到測試結果。

DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer xcodebuild -project IslandFlow.xcodeproj \
  -scheme IslandFlow -only-testing:IslandFlowUITests \

## 除錯旗標（只在 Debug 建置有效）

Xcode → Edit Scheme → Run → Arguments：

| 旗標 | 作用 |
|---|---|
| `account=t-demo` | 直接以指定身分登入（`t-demo` `t-demo2` `m-lake` `m-tea` `m-onsen` `a-gov`） |
| `tab=3` | 開在指定分頁 |
| `reset-demo` | 啟動時重置示範資料 |
| `open-mission=M-A` | 旅客直接打開某任務詳情 |
| `demo-progress=departed` | 小綠自動加入 M-A 並跑到指定階段（`joined` `departed` `completed` `token` `redeemed`），排練用；`token` 會留一張待核銷的兌換碼 |
| `show-welcome` | 強制顯示歡迎頁 |
| `demo-time=09:30` | 把「現在幾點」固定在指定時刻，只影響首頁班次是否已發車的排序與標示（帳本、站牌碼、兌換碼仍用真實時間）；UI 測試用它讓推薦固定是 10:40 |
| `layout-width=320` | 把整個畫面壓到指定寬度，檢查 320pt 版面（iOS 17 已沒有 320pt 機型）。注意 sheet 不受影響 |

UI 測試可用環境變數加旗標：`TEST_RUNNER_EXTRA_ARGS="layout-width=320" xcodebuild ... test`

## 已知限制（公開展示前要知道）

- **資料只存在單機。** 兩支手機之間不同步，所以兌換／核銷要在同一支手機切身分。正式版要接後端（規格書的 Supabase）
- **簽章金鑰寫在 App 裡**，只為展示「碼不能竄改、會過期」；正式版必須由伺服器簽發驗證
- 載客率、商家、歷史紀錄、天氣分數是模擬資料；碳排係數（自用車 0.115、公車 0.040 kgCO₂e/人公里）
  是示範值，公開前要換成可引用來源並記錄版本。旅客端只顯示「本段搭公車排放估算」，不宣稱減碳；
  管理端儀表板的「估算避免排放」仍是舊算法（全部完成者套自用車基準），見開發筆記 K21
- 唯讀路線目錄只有站名與站序，沒有班表、票價、即時資訊；匯入路線不會開任務
- 路線距離是站點直線距離 × 1.4 繞行係數估的（開放資料沒有路線線型）
- 商家名稱全部虛構；App 圖示是暫時的，等設計隊友的規範
- 旅綠幣換算價值（1 枚 = NT$1）、每日上限等仍屬規格書「需由團隊確認的決策」，都可在管理端調
